
# AI Systems Engineering Curriculum  
  
## Learning AI Architecture by Building an Immigration Policy Analyst System  
  
**Version:** 24 August 2026  
  
## Purpose  
  
This programme is designed to develop **genuine technical understanding  
of modern AI systems**, rather than the ability to produce apparently  
sophisticated software through AI-assisted coding.  
  
The objective is not to retrain as a generic software engineer or to  
qualify immediately for a senior AI Engineer role. The role that  
prompted this exercise is instead used as a **technology map**: Python  
and software engineering, APIs, LLMs, retrieval and RAG, tools and  
orchestration, agent frameworks, evaluation, deployment, observability  
and human-in-the-loop controls.  
  
The programme should ultimately enable me to:  
  
-  understand how LLM-powered systems are designed and implemented;  
-  write, read, test and debug meaningful Python code;  
-  understand APIs and the boundary between an application and an LLM;  
-  understand retrieval, embeddings and RAG from first principles;  
-  understand tools, state, routing, workflows and agents;  
-  recognise unnecessary complexity and AI-generated code slop;  
-  understand evaluation and regression testing;  
-  understand production architecture at a useful level;  
-  identify where judgment and control reside within an AI system;  
-  analyse what "human in the loop" actually means technically;  
-  connect technical architecture with governance and professional  
responsibility;  
-  communicate effectively with AI and software engineers; and  
-  design, build, test and defend an Immigration Policy Analyst System.  
  
The principal learning sequence is:  
  
> **Concept → manual implementation → failure → diagnosis →  
> understanding → simplification → abstraction → framework**  
  
------------------------------------------------------------------------  
  
# Part I --- Governing Learning Principles  
  
Four disciplines govern the programme:  
  
> **Understand before abstracting.**\  
> **Test before trusting.**\  
> **Simplify before extending.**\  
> **Resume rather than restart.**  
  
## 1. No code without comprehension  
  
No code should become part of the project unless I can explain what it  
does.  
  
The fact that code runs, passes a demonstration, was generated by a  
sophisticated AI, uses accepted frameworks, or looks professional does  
not establish that I understand it or that it is good software.  
  
Where AI generates code, I should understand it before incorporating it  
into the project.  
  
## 2. Working code is not the endpoint  
  
Whenever a significant feature works:  
  
1.  commit the working version to Git;  
2.  run the existing tests;  
3.  examine the implementation;  
4.  identify duplication and unnecessary complexity;  
5.  simplify where appropriate;  
6.  rerun the tests;  
7.  commit the simplified version.  
  
The distinction is between **making something work** and **understanding  
why it works and making it maintainable**.  
  
## 3. Prefer the simplest adequate architecture  
  
For every significant design decision ask:  
  
> **What is the simplest architecture that reliably solves this  
> problem?**  
  
And especially:  
  
> **Does an LLM actually need to make this decision?**  
  
A multi-agent system is not inherently better than a single-agent  
system. An agent is not inherently better than a deterministic workflow.  
A framework is not inherently better than ordinary Python.  
  
## 4. Frameworks come after concepts  
  
Initially use ordinary Python and direct APIs wherever reasonably  
possible.  
  
LangChain, LangGraph and Google ADK should be introduced only after  
encountering the problems they abstract.  
  
## 5. The programme is milestone-based, not calendar-based  
  
The programme assumes disruption.  
  
Four to eight focused hours per week is an indicative rhythm, not a  
quota. There is no concept of being "three weeks behind".  
  
If work stops for several weeks:  
  
> **Resume from the last completed, tested Git commit.**  
  
A missed month is not a failed programme.  
  
## 6. Build one system deeply  
  
Build one increasingly sophisticated Immigration Policy Analyst System  
rather than several superficial portfolio projects.  
  
Each version should solve a problem exposed by the previous version.  
  
## 7. Maintain an evidence trail  
  
The repository should eventually contain:  
  
``` text  
README.md  
LEARNING_RULES.md  
FAILURES.md  
DECISIONS.md  
src/  
tests/  
data/  
evaluation/  
experiments/  
```  
  
`FAILURES.md` records significant technical failures. `DECISIONS.md`  
records important architectural choices and their rationale.

# Part II --- AI Learning Rules  
  
These rules apply to ChatGPT, Claude, Claude Code, Copilot and other AI  
coding systems used during the programme. They should be stored as  
`LEARNING_RULES.md` in the repository.  
  
## Stage A --- AI as Tutor  
  
During programming and software-engineering foundations:  
  
**Do not solve programming exercises or write complete implementations  
for me.**  
  
When I encounter an error:  
  
1.  help me read and understand the error message;  
2.  ask me what I think caused it;  
3.  direct my attention to the relevant part of my code;  
4.  provide progressively stronger hints;  
5.  explain the underlying concept;  
6.  provide example code only when explanation and hints have not been  
sufficient.  
  
Do not immediately replace broken code with working code.  
  
When reviewing my code, distinguish between correctness problems, bugs,  
unnecessary complexity, duplication, poor Python practice,  
security/reliability problems and concepts I have not yet learned.  
  
Do not introduce an abstraction, design pattern, library or framework  
merely because it appears sophisticated.  
  
Periodically ask me to explain what a function does, its inputs and  
outputs, why a data structure was chosen, and how it could fail.  
  
## Stage B --- AI as Reviewer and Pair Programmer  
  
Once I can independently write and debug modest Python applications, AI  
may provide more substantial assistance.  
  
Appropriate uses include:  
  
-  reviewing an implementation for unnecessary complexity without  
rewriting it;  
-  comparing possible approaches and explaining trade-offs;  
-  identifying duplication;  
-  identifying missed edge cases;  
-  challenging whether a task should be deterministic or LLM-driven;  
-  helping design tests before changing code.  
  
AI-generated code may be used only after it has been inspected and  
understood.  
  
## Stage C --- AI as Engineering Assistant  
  
Once I have enough fluency to recognise poor generated code, AI coding  
agents may implement larger pieces of defined functionality.  
  
Generated code must remain understandable, reviewable, tested,  
justified, maintainable and refactorable.  
  
## The 2× Rule  
  
During the learning stages, an AI should generally not generate more  
code than I can reasonably inspect and explain during that study  
session.  
  
When a large implementation is suggested, ask:  
  
> **What is the simplest version of this that demonstrates the  
> concept?**  
  
## Anti-Slop Rule  
  
For substantial AI-generated implementations, examine:  
  
-  unnecessary classes and abstractions;  
-  duplicated logic;  
-  excessive dependencies;  
-  premature optimisation;  
-  functions doing too many tasks;  
-  needless architectural layers;  
-  comments that merely restate obvious code;  
-  sophistication without an identified problem.  
  
Periodically conduct deliberate code-reduction exercises:  
  
``` text  
Before: ___ lines  
After: ___ lines  
  
Behaviour changed: Yes / No  
Tests passed: Yes / No  
  
What was unnecessary?  
What did the simplification teach me?  
```  
  
The objective is **conceptual economy**, not minimum line count.

# Part III --- Continuous Evaluation Dataset  
  
Evaluation begins on **Day 1**.  
  
Create:  
  
``` text  
evaluation/  
cases/  
```  
  
Whenever a difficult immigration-law or policy problem occurs to me,  
record it even if the application cannot yet answer it.  
  
Example:  
  
``` text  
CASE-001  
  
Question:  
What provision applied on [date]?  
  
Why difficult:  
The provision was subsequently amended.  
  
Relevant sources:  
[...]  
  
Expected legal proposition:  
[...]  
  
Likely AI trap:  
Retrieves the current provision because it has stronger  
semantic similarity than the historically applicable provision.  
  
Status:  
System not yet capable of testing this case.  
```  
  
Cases should eventually cover commencement, transitional arrangements,  
overlapping routes, similar terminology, repealed or superseded  
provisions, Rules versus guidance, exceptions, cross-references and  
ambiguous policy language.

# Part IV --- Curriculum  
  
## Phase 0 --- Development Environment  
  
**Indicative effort:** about 12--15 focused hours, commonly spread  
across 1--2 weeks.  
  
### Objective  
  
Understand the environment in which software is actually created.  
  
### Learn  
  
-  terminal/command line;  
-  files, directories and paths;  
-  VS Code or equivalent editor;  
-  PowerShell on Windows;  
-  Python installation and the interpreter;  
-  packages and dependencies;  
-  virtual environments;  
-  Git repositories, staging, commits, branches and diffs;  
-  restoring earlier versions;  
-  environment variables;  
-  API-key security.  
  
### Recommended Phase 0 Learning Resources  
  
#### 1. VS Code --- Getting Started  
  
**Microsoft Visual Studio Code: Getting Started**  
  
https://code.visualstudio.com/docs/getstarted/getting-started  
  
Use this to understand the editor, opening folders, creating/editing  
files and the basic workspace.  
  
Then use:  
  
**VS Code --- Getting Started with the Terminal**  
  
https://code.visualstudio.com/docs/terminal/getting-started  
  
Focus on what a shell is, opening the integrated terminal, running  
commands, and understanding the working directory.  
  
Initially become comfortable with a small PowerShell vocabulary such as:  
  
``` powershell  
pwd  
cd  
dir  
mkdir  
echo  
type  
cls  
```  
  
Do not try to memorise large numbers of commands. The important  
questions are:  
  
-  Where am I?  
-  What directory am I working in?  
-  Is this a file or a directory?  
-  What does this path refer to?  
-  What program am I asking Windows to execute?  
  
#### 2. Git --- Learn the Concept Before the Commands  
  
**Official Git Learn resources**  
  
https://git-scm.com/learn  
  
Start with introductory material explaining:  
  
-  What is version control?  
-  What is Git?  
-  Why keep a history of changes?  
  
Then use:  
  
**Pro Git --- Chapter 1: Getting Started**  
  
https://git-scm.com/book/en/v2/Getting-Started-About-Version-Control  
  
and the early sections of:  
  
**Pro Git --- Chapter 2: Git Basics**  
  
https://git-scm.com/book/en/v2/Git-Basics-Getting-a-Git-Repository  
  
For Phase 0 concentrate on:  
  
``` text  
git init  
git status  
git add  
git commit  
git log  
git diff  
```  
  
and learn how to recover safely from a simple unwanted change.  
  
Do **not** introduce GitHub yet. First understand Git locally.  
  
#### 3. Python on Windows  
  
**Official Python documentation --- Using Python on Windows**  
  
https://docs.python.org/3/using/windows.html  
  
The important conceptual distinction is:  
  
> **VS Code is not Python.**  
  
VS Code is an editor/development environment. The Python interpreter is  
a separate program that executes Python code. The VS Code Python  
extension is another separate component.  
  
#### 4. Python Virtual Environments  
  
**Official Python Tutorial --- Virtual Environments and Packages**  
  
https://docs.python.org/3/tutorial/venv.html  
  
Understand the problem virtual environments solve before memorising  
commands.  
  
Conceptually:  
  
``` text  
Project A → its Python dependencies  
Project B → its Python dependencies  
```  
  
Each project can have an isolated environment so that incompatible  
package requirements do not interfere with one another.  
  
Understand what happens when using a command such as:  
  
``` text  
python -m venv .venv  
```  
  
rather than simply copying it.  
  
#### 5. Python in VS Code  
  
**Microsoft --- Python in Visual Studio Code Quick Start**  
  
https://code.visualstudio.com/docs/python/python-quick-start  
  
Use this after the preceding material to bring the components together.  
  
The mental model should become:  
  
``` text  
Windows  
|  
+-- filesystem  
|  +-- immigration-ai-lab/  
|  
+-- PowerShell  
+-- Git  
+-- Python  
+-- virtual environment  
  
VS Code  
|  
+-- edits/displays files  
+-- provides an integrated terminal  
+-- integrates with Git  
+-- integrates with Python  
```  
  
### Phase 0 Learning Process  
  
Aim for roughly **30% reading/tutorial and 70% doing**.  
  
Do not simply watch demonstrations.  
  
After learning a concept, deliberately use it.  
  
Examples:  
  
-  after learning `mkdir`, create directories from PowerShell rather  
than Explorer;  
-  after learning `git diff`, modify a file and inspect the actual  
diff;  
-  after learning commits, make several small commits and inspect the  
history;  
-  deliberately alter or delete something and recover it;  
-  create a virtual environment and explain what changed on disk.  
  
### Phase 0 Final Project  
  
Create `immigration-ai-lab` **yourself**.  
  
AI should not create the repository automatically.  
  
Build the initial structure manually while understanding each operation:  
  
``` text  
immigration-ai-lab/  
README.md  
LEARNING_RULES.md  
FAILURES.md  
DECISIONS.md  
src/  
tests/  
data/  
evaluation/  
cases/  
experiments/  
```  
  
Initialise Git and make the first commit.  
  
Then deliberately change or delete something, inspect what Git reports  
and restore it.  
  
### Phase 0 Completion Gate  
  
Without assistance, explain:  
  
-  repository;  
-  commit;  
-  branch;  
-  dependency;  
-  virtual environment;  
-  source file;  
-  working directory;  
-  path;  
-  terminal/shell;  
-  Python interpreter.  
  
Do not progress merely because AI can perform these operations.  
  
### Do Not Learn Yet  
  
Avoid adding unnecessary cognitive load through:  
  
-  Docker;  
-  WSL/Linux;  
-  GitHub Actions;  
-  CI/CD;  
-  Git rebasing;  
-  SSH configuration;  
-  Conda;  
-  Poetry;  
-  advanced Python packaging;  
-  cloud environments;  
-  elaborate VS Code customisation.  
  
These can be introduced when the project creates a reason to understand  
them.

## Phase 1 --- Python Foundations  
  
**Indicative duration:** 4--6 weeks.  
  
### Objective  
  
Write, test and debug small Python programs independently.  
  
### Learn  
  
Variables, strings, numbers, Booleans, lists, dictionaries, tuples,  
sets, conditions, loops, functions, arguments, return values, scope,  
modules, imports, files, paths, CSV, JSON, exceptions, tracebacks, basic  
classes and type hints.  
  
### Training Resources  
  
**Primary:** Python for Everybody --- Charles Severance / University of  
Michigan\  
https://www.py4e.com/  
  
**Secondary:** Automate the Boring Stuff with Python --- Al Sweigart\  
https://automatetheboringstuff.com/  
  
**Reference:** Official Python Tutorial\  
https://docs.python.org/3/tutorial/  
  
### Exercises  
  
Before using AI APIs build a word-frequency analyser, heading extractor,  
CSV reader, JSON converter, text-search utility and paragraph parser.  
  
### Immigration Mini-Project  
  
Build an **Immigration Rules Parser** that takes Rules text and extracts  
structured information such as Part, Appendix, Heading, Paragraph and  
Text, exporting the result to JSON.  
  
### Completion Gate  
  
I can sit in front of an empty Python file and write a modest program  
myself. I can deliberately break it and use the traceback to identify  
the problem.

## Phase 2 --- Software Engineering Foundations  
  
**Indicative duration:** 2--4 weeks.  
  
Learn decomposition, functions versus classes, separation of concerns,  
modules, naming, configuration, logging, type hints, unit/integration  
testing, refactoring, Git branching, code review, dependencies and  
technical debt.  
  
**Resources:**  
  
-  pytest Getting Started:  
https://docs.pytest.org/en/stable/getting-started.html  
-  Pro Git: https://git-scm.com/book/en/v2  
  
Write tests for the Immigration Rules Parser and refactor it without  
changing behaviour.  
  
------------------------------------------------------------------------  
  
## Phase 3 --- HTTP, APIs and JSON  
  
**Indicative duration:** 2 weeks.  
  
Learn client/server architecture, HTTP requests/responses, endpoints,  
headers, authentication, GET/POST, JSON, status codes, timeouts, retries  
and rate limits.  
  
**Resources:**  
  
-  MDN HTTP overview: https://developer.mozilla.org/en-US/docs/Web/HTTP  
-  FastAPI Tutorial: https://fastapi.tiangolo.com/tutorial/  
  
Call a simple external API from Python, inspect and parse its response,  
handle failure, and later expose one of my own Python functions through  
FastAPI.  
  
------------------------------------------------------------------------  
  
## Phase 4 --- LLM Fundamentals  
  
**Indicative duration:** 2--3 weeks.  
  
Learn training versus inference, tokens, context windows,  
prompts/instructions, sampling, hallucination, structured output, tool  
calling, latency and cost. Understand neural networks, transformers,  
attention and embeddings conceptually.  
  
**Resources:**  
  
-  DeepLearning.AI --- ChatGPT Prompt Engineering for Developers  
-  Current primary documentation from the model provider being used for  
API calls, structured output and tool calling.  
  
### Project v0.1  
  
`Question → Python → LLM API → Answer`  
  
No LangChain, LangGraph or agent framework.  
  
Then add structured output as v0.2 and record failures in `FAILURES.md`.  
  
------------------------------------------------------------------------  
  
## Phase 5 --- Information Retrieval and Embeddings  
  
**Indicative duration:** 3 weeks.  
  
Learn keyword search, semantic search, embeddings, vectors, similarity,  
ranking, metadata, filtering, precision, recall, false positives and  
false negatives.  
  
Search a small corpus of Immigration Rules and record both **relevance**  
and **legal applicability**.  
  
Core insight:  
  
> **Successful retrieval is not the same thing as correct legal  
> retrieval.**  
  
------------------------------------------------------------------------  
  
## Phase 6 --- Manual RAG  
  
**Indicative duration:** 3--4 weeks.  
  
Learn ingestion, chunking, embeddings, indexing, retrieval, context  
construction, metadata, grounding and citations.  
  
Build:  
  
`Question → Retrieve evidence → Inspect evidence → Construct context → LLM → Answer → Sources`  
  
Find examples of correct retrieval/correct answer, correct  
retrieval/incorrect answer, incorrect retrieval/plausible answer,  
insufficient evidence and contradictory evidence.  
  
### Explanation Checkpoint 1  
  
Explain to an intelligent non-engineer:  
  
> **How can a RAG system give a wrong answer even though it has access  
> to the correct documents?**  
  
------------------------------------------------------------------------  
  
## Phase 7 --- Legal Source Architecture and Temporal Validity  
  
**Indicative duration:** 4--6 weeks.  
  
Introduce source metadata such as source type, title, paragraph,  
version, effective-from/effective-to dates, authority and jurisdiction.  
  
Distinguish Rules, Statements of Changes, policy guidance, operational  
guidance and other relevant material.  
  
Build temporal retrieval capable of answering:  
  
> **What was the applicable position on DATE?**  
  
Investigate commencement, transitional provisions, amendments,  
superseded provisions, source hierarchy and Rules/guidance  
inconsistency.  
  
Core question:  
  
> **How does the system distinguish relevance from legal  
> applicability?**  
  
### Explanation Checkpoint 2  
  
Explain why an AI can retrieve a highly relevant legal provision and  
still be legally wrong.  
  
------------------------------------------------------------------------  
  
## Phase 8 --- Tools and Deterministic Workflows  
  
**Indicative duration:** 2--3 weeks.  
  
Learn tool calling, deterministic functions, validation, retries,  
fallbacks, state and routing.  
  
Potential tools include `retrieve_rules()`, `retrieve_guidance()`,  
`find_version()`, `compare_versions()` and `get_source_metadata()`.  
  
For every operation ask:  
  
> **Why is an LLM involved here?**  
  
Use ordinary software where it is more reliable.  
  
------------------------------------------------------------------------  
  
## Phase 9 --- Workflow and Agent Architecture  
  
**Indicative duration:** 3--4 weeks.  
  
Learn state, nodes, transitions, conditional routing, loops, retries,  
checkpoints, memory and escalation.  
  
For every proposed node identify its purpose, input, output, whether it  
is deterministic or probabilistic, failure modes, failure detection,  
transition criteria and responsible decision-maker.  
  
Core question:  
  
> **Where does control actually reside?**  
  
------------------------------------------------------------------------  
  
## Phase 10 --- LangGraph  
  
**Indicative duration:** 2--3 weeks.  
  
Only now introduce LangGraph.  
  
**Resources:**  
  
-  Official LangGraph documentation:  
https://docs.langchain.com/oss/python/langgraph/overview  
-  LangChain Academy: https://academy.langchain.com/  
  
Reimplement an existing manual workflow in LangGraph and compare it with  
plain Python: what became simpler, more complicated, hidden or more  
observable?  
  
------------------------------------------------------------------------  
  
## Phase 11 --- LangChain and Google ADK  
  
**Indicative duration:** 2--3 weeks.  
  
Compare frameworks rather than becoming attached to one.  
  
**Resources:**  
  
-  LangChain documentation: https://docs.langchain.com/  
-  Google ADK documentation: https://google.github.io/adk-docs/  
  
Compare a small workflow implemented in plain Python, LangGraph,  
LangChain where appropriate, and Google ADK.  
  
Assess transparency, code volume, complexity, testability, debugging,  
control, dependencies and lock-in.  
  
------------------------------------------------------------------------  
  
## Phase 12 --- Formal Evaluation  
  
**Indicative duration:** 3--4 weeks.  
  
Formalise the evaluation corpus accumulated since Day 1.  
  
Learn evaluation datasets, precision, recall, retrieval accuracy, answer  
correctness, groundedness, citation accuracy, regression testing and  
human evaluation.  
  
Whenever model, prompt, chunking, embeddings, retrieval, architecture or  
framework changes, rerun the evaluation suite.  
  
A newer model or more sophisticated architecture is not presumed to be  
better.  
  
------------------------------------------------------------------------  
  
## Phase 13 --- Human-in-the-Loop and Governance  
  
**Indicative duration:** 3--4 weeks.  
  
Turn "human oversight" into an engineered mechanism.  
  
Investigate escalation triggers, who decides review is necessary,  
whether model confidence is meaningful, which triggers can be  
deterministic, what evidence the reviewer receives, the reviewer's  
authority, and how intervention is recorded.  
  
Add an audit trail covering appropriate information about questions,  
time, model/version, configuration, retrieved documents and versions,  
tool calls, routing, answers, citations, review triggers and final  
output.  
  
### Explanation Checkpoint 3  
  
Explain:  
  
> **What does "human in the loop" actually mean in this system?**  
  
------------------------------------------------------------------------  
  
## Phase 14 --- Production Fundamentals  
  
**Indicative duration:** 3--4 weeks.  
  
Learn application configuration, secrets, SQL basics, authentication,  
permissions, APIs, logging, Docker conceptually, cloud deployment  
conceptually, CI/CD, monitoring, observability and recovery.  
  
The objective is architectural literacy, not becoming a  
cloud-infrastructure specialist.  
  
Expose the application through an API and ultimately deploy a controlled  
demonstration.  
  
------------------------------------------------------------------------  
  
## Phase 15 --- Final Architecture Review  
  
Without consulting the code, draw the architecture.  
  
For every component explain why it exists, its input/output,  
deterministic versus probabilistic behaviour, why AI is or is not used,  
dependencies, failure modes, testing, logging, security, human  
intervention and governance implications.  
  
Then open the repository and identify where each architectural element  
is implemented.  
  
Finally answer:  
  
> **Which components would I remove if required to simplify this system  
> by 30%?**  
  
------------------------------------------------------------------------  
  
# Part V --- Indicative Rhythm and Milestones  
  
At roughly **4--8 focused hours per week**, expect approximately **9--15  
months of elapsed time**, including interruptions.  
  
This is an estimate, not a deadline. Progress is measured by completion  
gates.  
  
Milestones are:  
  
1.  **Programming literacy** --- write and debug small Python  
applications without AI writing them.  
2.  **Software literacy** --- structure, version, test and refactor a  
small application.  
3.  **LLM application literacy** --- understand the application/model  
boundary and use an LLM API directly.  
4.  **Retrieval literacy** --- understand semantic retrieval and its  
failure modes.  
5.  **RAG literacy** --- build and explain RAG without an orchestration  
framework.  
6.  **Domain AI engineering** --- represent source authority, versions  
and temporal validity.  
7.  **Agent architecture literacy** --- understand tools, state,  
routing, retries, fallbacks and escalation independently of a  
framework.  
8.  **Framework literacy** --- critically compare LangGraph, LangChain  
and Google ADK.  
9.  **Evaluation literacy** --- demonstrate empirically whether changes  
improve or damage performance.  
10. **Governance literacy** --- identify where control, judgment,  
escalation and accountability reside.  
11. **AI systems literacy** --- communicate meaningfully with engineers,  
inspect implementation code and challenge unnecessary complexity.  
  
# Final Standard  
  
Success is not:  
  
> **I used AI to build an Immigration Policy Analyst Agent.**  
  
Nor is it:  
  
> **I completed courses in Python, LangChain and LangGraph.**  
  
Success is:  
  
> **I designed and built an AI-assisted legal/policy system that I  
> understand. I can explain its architecture, inspect and challenge its  
> code, test its behaviour, identify its failure modes, distinguish  
> retrieval from legal applicability, simplify unnecessary complexity,  
> show where human judgment and machine judgment enter the workflow, and  
> defend the choices I made.**  
  
The Immigration Policy Analyst System is the vehicle for learning.  
  
**The product is the understanding required to build it.**
